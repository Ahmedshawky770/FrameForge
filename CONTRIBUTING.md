## Code of Conduct

This project follows the [Contributor Covenant Code of Conduct](https://www.contributor-covenant.org/version/2/1/code_of_conduct/). By participating, you are expected to uphold this code. Please report unacceptable behavior to the maintainers.

## Getting Started

### Prerequisites
- Rust 1.75+ (see `rust-toolchain.toml`)
- Node.js 20+ (for web component)
- System dependencies (Pop!_OS/Ubuntu 22.04+):
  ```bash
  sudo apt install -y libmpv-dev libavcodec-dev libavformat-dev libswscale-dev \
    libswresample-dev libavfilter-dev libavutil-dev libwebkit2gtk-4.0-dev \
    libgtk-3-dev libssl-dev pkg-config build-essential
  ```

### Clone and Build
```bash
git clone https://github.com/your-org/FrameForge.git
cd FrameForge
cargo tauri dev  # Development mode with hot reload
```

### Run Tests
```bash
cargo test --workspace          # All headless tests
cargo test -p frameforge-scrub-engine -- --ignored  # Golden frame tests (requires test-media)
```

## Development Workflow

### Branch Strategy
- `main` — Stable releases only
- `develop` — Integration branch (if used)
- Feature branches: `feat/<short-description>`
- Fix branches: `fix/<short-description>`
- Docs branches: `docs/<short-description>`

### Commit Messages
Follow [Conventional Commits](https://www.conventionalcommits.org/):
```
<type>[optional scope]: <description>

[optional body]

[optional footer(s)]
```

Types: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `chore`, `build`, `ci`

Examples:
```
feat(scrub-engine): add prev_frame for frame-accurate reverse scrub
fix(export-engine): handle DTS monotonicity at segment boundaries
docs(specs): update public-api to match current implementation
```

### Pre-commit Checks
Before pushing, run:
```bash
cargo fmt --check
cargo clippy --all-targets -- -D warnings
cargo test --workspace
```

## Code Standards

### Rust
- Edition 2021
- `rustfmt` default style (run `cargo fmt`)
- `clippy` with `-D warnings` (no warnings allowed)
- Public APIs must have doc comments (`///`)
- Use `thiserror` for error types, `anyhow` only in binaries
- Prefer `Result<T, FrameForgeError>` over `anyhow::Result`
- No `unwrap()`/`expect()` in production code — handle errors explicitly

### TypeScript/JavaScript
- ES modules (`type: "module"`)
- No framework dependencies in Tauri frontend (vanilla JS + Vite)
- Web component: standard Custom Elements API
- JSDoc comments for public APIs

### General
- **Headless-first**: Core crates (`crates/*`) must not depend on GUI/Tauri/WebKitGTK
- **Dependency direction**: `apps/tauri-app` → `crates/*` — never reverse
- **No zero-copy claims** across WebView boundary — label copies as "low-copy"
- **Dynamic linking** preferred for libmpv/FFmpeg (LGPL compliance)
- **Atomic writes**: Always use temp file + rename for output files

## Testing

### Test Categories
1. **Unit tests** — In each crate's `src/lib.rs` under `#[cfg(test)]`
2. **Integration tests** — In `crates/*/tests/*.rs`
3. **Golden-frame tests** — `crates/scrub-engine/tests/golden_frame.rs` (requires test-media)
4. **Merge compatibility tests** — `crates/edit-engine/tests/merge_compatibility.rs`
5. **CLI smoke tests** — Manual `cargo run --bin frameforge-cli ...`

### Running Tests
```bash
# All tests (fast, headless)
cargo test --workspace

# With golden-frame tests (requires test-media files)
cargo test --workspace -- --ignored

# Specific test
cargo test -p frameforge-edit-engine merge_overlapping_segments_rejected
```

### Test Media
- `test-media/test-video.mp4` — committed (216 MB)
- Other files: generated by scripts or fetched via `corpus.yaml` checksums
- Golden-frame hashes: regenerate only on intentional codec/mpv version change

## Documentation

### Documentation Files
- `README.md` — Project overview, quick start
- `specs/01-executive-summary.md` through `specs/12-risk-register.md` — Full specifications
- `specs/11-readme.md` — Developer quick reference
- `packages/media-player/README.md` — Web component docs
- `packaging/README.md` — Packaging notes
- Code comments — Public APIs must have `///` docs

### Updating Documentation
- **Keep docs in sync with code** — Update specs when implementation changes
- **No speculative docs** — Document what exists, not what's planned
- **ADR updates** — When making architectural changes, update `specs/05-adrs.md`
- **Risk register** — Add new risks to `specs/12-risk-register.md`

## Pull Request Process

### Before Opening PR
1. Ensure all pre-commit checks pass
2. Update relevant documentation
3. Add tests for new functionality
4. Run full test suite

### PR Requirements
- Clear title following Conventional Commits
- Description of changes and rationale
- Link to related issue (if any)
- Screenshots for UI changes
- Updated `specs/` if behavior changed

### Review Process
- At least one maintainer approval required
- CI must pass (clippy, fmt, tests, build)
- No unresolved review comments

### Merge Strategy
- Squash and merge to `main`
- Delete branch after merge
- Version bump in `Cargo.toml` workspace for releases

## Architecture Decisions

Major architectural changes require an **ADR** (Architecture Decision Record):
1. Create/update entry in `specs/05-adrs.md`
2. Include: Decision, Rationale, Trade-offs, Alternatives, Verification needed
3. Reference ADR in PR description
4. Get maintainer consensus before implementation

See existing ADRs for examples:
- ADR-1: libmpv vs custom playback
- ADR-2: Video presentation strategy
- ADR-3: IPC transport
- ADR-4: Hardware acceleration
- ADR-5: Lossless vs re-encode
- ADR-6: i18n framework
- ADR-7: Packaging
- ADR-8: Frontend framework
- ADR-9: Timebase
